# v0.4.72

## Feature: `inArrayOpt` / `notInArrayOpt` — `IN` up to a threshold, one array parameter above it

[v0.4.71](v0.4.71.md) added `eqAny` / `neAll` and left the choice to the call site: the `IN ($1, $2, …)`
list, whose text changes with every list length, or the array form, whose text does not. Measuring
the two under `preparedStatements` (PostgreSQL 18, 2026-09-06) showed the choice is not a matter of
taste but of list length:

- Up to about ten elements the fixed-length `IN` text is the better prepared statement: PostgreSQL
  gives it a cached generic plan after five executions, while `= ANY($1)` is re-planned on every
  call — its generic plan has to assume ~10 elements, so the custom plan keeps winning the cost
  comparison — and only reaches a generic plan from roughly 30 elements on.
- Above that the array form costs nothing extra in planning, and every extra `IN` length is another
  statement text and another cached plan per pooled connection: a 100 VU purchase journey put 12
  length variants of one lookup and 11 of another into every connection's cache.

`inArrayOpt` picks per call:

```typescript
db.products.where(p => inArrayOpt(p.id, productIds));
// productIds.length <= threshold:  "product"."id" IN ($1, $2, $3)
// productIds.length  > threshold:  "product"."id" = ANY($1::integer[])

db.products.where(p => notInArrayOpt(p.id, excludedIds));   // NOT IN (…)  /  <> ALL($1::integer[])
```

Results are identical to `inArray` / `notInArray` for every list, the empty one included (`1=0` /
`1=1`); only the statement text differs. Constant lists (enum members) stay well under the threshold
and keep their exact-length `IN` text and planner estimate, so replacing every `inArray` whose
argument is an array is safe.

### The threshold is configurable — through `LinkgressConfig`

Default `8` (`LinkgressConfig.DEFAULT_IN_ARRAY_OPT_THRESHOLD`). The operators are plain functions
used inside `where(...)` lambdas with no context in reach, so the setting is process-wide, and it
is set through the new **`LinkgressConfig`** static class — the public surface for every
library-wide setting from here on:

```typescript
import { LinkgressConfig } from 'linkgress-orm';

LinkgressConfig.inArrayOptThreshold = 12;                // property setter
LinkgressConfig.configure({ inArrayOptThreshold: 12 });  // several settings at once
LinkgressConfig.inArrayOptThreshold;                     // -> 12
LinkgressConfig.resetToDefaults();                       // test isolation

new AppDatabase(client, { inArrayOptThreshold: 12 });    // QueryOptions at construction writes the same value
```

`0` sends every non-empty list to the array form. A threshold that is not a non-negative integer
is rejected and the current value stays. The last write wins, whichever path it came through.

Internally the threshold is a module-level variable next to `inArrayOpt`, so the hot-path read is a
plain variable access; the functions that write it (`setInArrayOptThreshold`,
`getInArrayOptThreshold`) are internal and are **not** exported from the package — `LinkgressConfig`
is the only way in.

Tests: `tests/queries/in-array-opt.test.ts` — the `LinkgressConfig` surface (default, setter/getter,
`configure`, `resetToDefaults`, validation, no package-level setter functions), the switch at, below
and above the threshold for both operators, the stable text above it, the casts, the empty list, the
`QueryOptions` path, and row-for-row parity with `inArray` / `notInArray` against PostgreSQL
including NULL handling.
