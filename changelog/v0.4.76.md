# v0.4.76

## Performance: one collection-marker `RegExp` per table, and the rewrite pass skipped when there is nothing to rewrite

Every collection projection is built against mock items whose column refs carry the marker
alias `"__collection_<table>__"` (see `CollectionQueryBuilder.createMockItem`), and every
strategy rewrites that marker back to the real inner alias while it assembles SQL — for every
selected field expression, the WHERE, the ORDER BY, the array/scalar aggregation field, and the
filter-join condition. All thirteen of those sites constructed the `RegExp` per call:

```typescript
const markerPattern = new RegExp(`"__collection_${targetTable}__"\\.`, 'g');
return expression.replace(markerPattern, `"${innerTableAlias}".`);
```

On a projection with a handful of nested collections that is dozens of `RegExp` constructions
and passes per build, on every build. The pattern is a pure function of the table name, so it is
now built once per (table, form) — `collectionMarkerPattern(table, withDot)` in `query-utils` —
and the lateral strategy skips the pass entirely when the expression cannot contain the marker
(`!expression.includes('"__collection_')`), which is the common case for plain column refs.

Measured on the gopass-eshop `order/create` burst (Node 26, one process, 200 concurrent guest
creates, V8 sampling profile, self time per 200 orders):

| function | before | after |
| --- | ---: | ---: |
| `rewriteTableReference` (lateral strategy, three closures) | 22.2 ms | 2.5 ms |
| lateral field-expression closure | 5.7 ms | 2.5 ms |
| `LateralCollectionStrategy.buildAggregation`, inclusive | 69.9 ms | 39.9 ms |

`buildJsonbAggregation`'s own self time is 14.0 ms in both profiles, which is the check that the
two profiles are comparable. Roughly 0.15 ms per create request, 1.5–2 % of its CPU; not a
throughput change you can see through run-to-run noise, a build-cost one. Same rewrite under Bun
was 0.9 % of process CPU in its own profile.

## `hasIndex` de-duplicates by name

A host that builds its entity model more than once per process — an application context and a
migration context, say — registered every index twice, because the metadata store is
class-static and `hasIndex` appended unconditionally. The schema reconcile then planned each
*new* index twice ("1. Create index CONCURRENTLY … 2. Create index CONCURRENTLY …"; the second
run hit `42P07 … already exists, skipping`). A repeated `hasIndex(name, …)` now REPLACES the
earlier entry, so the latest definition wins and the plan carries each index once.

Tests: `tests/queries/collection-marker-pattern-and-index-dedup.test.ts` — the cached pattern
rewrites exactly like the inline one in both forms (with and without the trailing dot) and does
not leak `lastIndex` state across calls; a repeated `hasIndex` registration yields one entry with
the last definition. Full suite green.
