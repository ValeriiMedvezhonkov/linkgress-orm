# v0.4.73

## `withPreparedStatements` on query builders

[v0.4.70](v0.4.70.md) put the per-query prepared-statement override on the table accessor:

```typescript
db.users.withPreparedStatements(false).where(u => eq(u.id, 1)).toList();
```

That is out of reach for code that receives an already-built query — a paginated-grid helper
that is handed `modelQuery` and adds the filter, the ordering, `limit`/`offset` and the count. Such
statements are exactly the ones a plan cache should not keep: their text changes with the request
(paging offsets, sort columns, filter combinations) and they run a few times a minute, so every
distinct text is a cached plan in every pooled connection for nothing.

The override is now also available on `QueryBuilder`, `SelectQueryBuilder` and `JoinQueryBuilder`,
at any point of the chain, covering every execution of that builder (`toList`, `count`,
`countOver`, `firstOrDefault`, …):

```typescript
query.orderBy(o => o.createdAt).limit(25).offset(250).withPreparedStatements(false).toList();
query.withPreparedStatements(false).count();
```

`true` opts a built query IN on an unprepared context, as on the accessor. Tests:
`tests/database/prepared-statements.test.ts` (a built query opted out leaves no named statement
for its page read or its count; opting in on an unprepared context names exactly one).

## Feature (opt-in): `LinkgressConfig.inArrayPadBuckets` — a bucket ladder for the sub-threshold band

[v0.4.72](v0.4.72.md)'s `inArrayOpt` collapses everything *above* its threshold into one statement
text. Below it, each list still renders one placeholder per element, so a family whose lists range
over 1…8 elements leaves eight texts — and eight cached plans — on every pooled connection. A ladder
collapses that band too: each list is rounded up to the next rung and the gap filled by **repeating
its last element**.

```typescript
import { LinkgressConfig } from 'linkgress-orm';

LinkgressConfig.inArrayPadBuckets = [1, 4, 8];
LinkgressConfig.inArrayPadBuckets = LinkgressConfig.DEFAULT_IN_ARRAY_PAD_BUCKETS;  // the same ladder
LinkgressConfig.configure({ inArrayPadBuckets: [1, 4, 8] });
new AppDatabase(client, { inArrayPadBuckets: [1, 4, 8] });   // QueryOptions writes the same value

db.widgets.where(w => inArrayOpt(w.slotId, [4, 8, 15]));
// off (default):    "w"."slot_id" IN ($1, $2, $3)         params [4, 8, 15]
// with [1, 4, 8]:   "w"."slot_id" IN ($1, $2, $3, $4)     params [4, 8, 15, 15]
```

**Off by default** — `null` until a consumer installs a ladder — because it trades an exact
per-length row estimate for fewer statement texts, and that is the consumer's call.

Repeating a value rather than padding with `NULL` is what makes this both safe and useful:
`x IN (a, b, b)` selects exactly what `x IN (a, b)` does and `x NOT IN (a, b, b)` exactly what
`x NOT IN (a, b)` does, so `notInArrayOpt` pads the same way — while PostgreSQL still counts the
placeholders when it estimates the predicate. A `NULL` fill would be recognised as matching nothing,
which both changes that estimate and, for `NOT IN`, changes the result.

**Choosing rungs.** Measured on PostgreSQL 18 with named prepared statements (2026-09-06), widening
is free at every width except the two smallest: a one-element list sent to a wider statement costs
about 32 %, a two-element list about 26 %, because the cached plan is then costed for a list several
times longer than the one that arrives. From three elements up the same widening is free — so a
ladder wants its low rungs tight and may collapse everything above. `[1, 4, 8]` keeps single-element
lookups exact, accepts the cost on two-element ones and folds 3…8 into two texts; `[1, 2, 8]` pays
nothing at all for the same number of texts.

Rungs must be positive integers in strictly ascending order; anything else throws and leaves the
current ladder in place. The stored ladder is a frozen copy, so a caller mutating its own array
afterwards cannot change it. An empty list keeps its constant (`1=0` / `1=1`) — there is no element
to repeat — and a non-array argument still degrades to that constant rather than throwing. A list
longer than the top rung is widened to the threshold instead, so raising `inArrayOptThreshold`
extends the ladder rather than dropping lengths out of it, and rungs above the threshold are simply
never reached.

Tests: `tests/queries/in-array-pad-buckets.test.ts` — the `LinkgressConfig` surface (default off,
published constant, setter/getter, frozen copy, `configure`, `resetToDefaults`, validation, no
package-level setter functions), the emitted SQL at every length in the band, the empty list, the
`NOT IN` form, the interaction with the threshold in both directions, and against PostgreSQL:
row-for-row parity with the unpadded lookup at each length 1…8, parity for `NOT IN` including NULL
handling, the band collapsing from eight statement texts to three on the wire, and the
`QueryOptions` path.

## Docs: `docs/guides/configuration.md` — one page for every option

The opt-in features of the last releases were each documented where they were implemented
(`logFailedQueries` and `preparedStatements` under Database Clients, `inArrayOpt` under
Querying) and several older options — `withTimeout`, `expectedExecutionTime`,
`onQueryTakingTooLong`, `slowQueryStackTraceLimit`, `traceTime`, `disableMappers`, `rawResult`,
`MockRowCache` — were documented nowhere at all. The new **Configuration & Options** guide is
the canonical list: every `QueryOptions` field with its default, the per-query overrides and
their precedence, `LinkgressConfig`, the opt-in query-build caches, and recipes for a production
context, a hot OLTP path and a reporting query.

Also in this pass:

- `withPreparedStatements` on already-built queries (`QueryBuilder`, `SelectQueryBuilder`,
  `JoinQueryBuilder`) is documented in Database Clients, Querying and the new guide — including
  that a grouped chain must set it before `.groupBy()`.
- The name collision is called out on both sides: `.prepare('name')` + `sql.placeholder()` is a
  CLIENT-side reusable query, `preparedStatements` is the SERVER-side named statement. They are
  independent.
- Getting Started gained an "Optional Features" table (what exists, one line each, where to
  turn it on) and `inArrayOpt` / `notInArrayOpt` in its operator list.
- The stale `QueryOptions` listing in Collection Strategies (six fields, last accurate several
  releases ago) now shows the current shape and points at the new guide.
- `PostgresClient`'s "automatic prepared statements" bullet was wrong — linkgress runs every
  statement through `unsafe()`, so statements are unnamed unless `preparedStatements` is on.
- Fixed two dead links in the Querying guide's See Also (`data-modification.md` →
  `insert-update-guide.md`, `CTE-GUIDE.md` → `cte-guide.md`).
