# v0.4.74

## `withPreparedStatements` on `QueryBatch`

A batch executes ONE statement for all of its registered queries, so the per-query
override from [v0.4.73](v0.4.73.md) could not reach it: the batch takes the executor of
its first query and requires every query to share it, and a builder-level override
produces a new executor per builder.

The batch now carries the override itself:

```typescript
const batch = new QueryBatch().withPreparedStatements(false);
batch.addList(db.cartItems.where(i => eqAny(i.id, ids)).select(i => ({ id: i.id })), 'items');
batch.addFirstOrDefault(db.users.where(u => eqAny(u.id, userIds)).select(u => u), 'buyer');
await batch.executeBatch();
```

Why a batch may want to opt out on a context that prepares everything else: a batch
whose branches all bind array parameters (`= ANY($n::type[])`) is typically re-planned
on every call by PostgreSQL — the generic plan cannot see the array sizes and loses the
cost comparison — so naming the statement keeps an unused generic plan and the rewritten
query tree in every pooled connection (0.6 MB per connection for a 5.6 KB order-side-data
batch, 2026-09-07 census) for no planning saved. Unnamed, the batch costs one describe
round trip and the same planning it was already doing.

`withPreparedStatements(true)` opts a batch IN on an unprepared context, symmetrically.

Tests: `tests/database/prepared-statements.test.ts` — the opted-out batch leaves no named
statement and returns the same rows and count as the standalone executions; the default
batch follows the context.
